## 分支开发规则

分支命名：

```text
codex/<功能简称>
```

每个功能分支必须有：

- 目标和用户价值。
- 依赖和前置条件。
- 明确 write set。
- 成功标准和失败边界。
- 预期测试路径。
- 不能做的外部操作。

建议第一批分支顺序：

1. `codex/feasibility-audit`：运行入口、依赖、AI 接口、数据库和部署边界审查。
2. `codex/content-positioning`：用户可见内容和产品定位调整。
3. `codex/ui-resource-relay`：首页、需求输入和匹配方案界面改造。
4. `codex/need-matching-flow`：需求结构化、匹配方案和缺口需求闭环。
5. `codex/demo-hardening`：演示数据、错误状态、权限边界和录屏路径。

不要在一个分支中同时改 UI、数据结构、Worker 鉴权和部署配置，除非依赖关系已经写明并由总控批准。

## 总控验收门槛

分支只能在满足以下条件后进入合并审查：

- 实际 diff 与 write set 一致。
- 本地可运行入口和运行方式已验证。
- 核心路径有代表性案例和至少一个边界案例。
- AI 失败时仍有可解释的降级路径。
- 没有新增明文凭证、未经授权的真实数据或无法解释的外部依赖。
- UI 改动经过浏览器可见检查，不能只依赖字符串扫描。
- 项目文档、PPT、演示视频计划和实际功能没有互相矛盾。
